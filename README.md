# Holdout findings

Holdout audits RL environments and agent benchmarks for reward hacks and grader bugs: ways an agent can score well without doing the task, and places where the grader scores work incorrectly. <!-- counts:start -->This repository collects the 27 issues we filed in 20 repositories across 17 organisations between 22 and 23 October 2026.<!-- counts:end --> Every finding was filed publicly as a GitHub issue on the affected repository. All but one include a reproduction script and its output; [huggingface/Repo2RLEnv#211](https://github.com/huggingface/Repo2RLEnv/issues/211) describes the code path and links the lines involved instead. Each folder under [`findings/`](findings/) holds a short summary and, where the issue included them, the script exactly as posted and the posted output.

Status values: **open** (no maintainer comment or review yet), **acknowledged** (a maintainer, meaning someone with owner, member or collaborator access, commented on the issue or commented on or reviewed a fix pull request), **fixed** (closed as completed, or a fix pull request, as defined below, was merged), **closed** (closed for another reason). Comments from bots and from us do not count.

Fix PR lists the pull requests with evidence that they fix the issue: GitHub lists them as closing it or they are linked to it (a later unlink removes them), they reference it with a closing keyword, or their title or body references it with fix, close or resolve wording. A pull request that only mentions the issue is not listed. Each is marked **ours** (opened by us) or **community** (opened by someone else), and **open**, **draft** (an open draft), **merged** or **closed**. "With an open fix PR" in the status line includes open drafts. "With no open fix PR" covers issues that are not fixed and have no open or draft fix pull request.

## How we test

- We run the repository's own scoring code at a pinned commit. Each finding records the commit, and where there is a repro, it calls the real grader, verifier or metric rather than a re-implementation of it.
- 26 of the 27 issues include a repro script and its output. The exception, huggingface/Repo2RLEnv#211, gives the code path, the line links and a static count of affected tasks instead.
- Repros run, or re-run, on Ubuntu 24.04 with the network disabled.
- No model or API calls. Where a grader uses an LLM judge, the judge is stubbed with fixed outputs, and the finding says so. Other stand-ins (for example a GPU training run replaced by a stub) are described in the finding as well.
- Each repro shows a control that fails, a correct solution that passes, and the shortcut that passes, where the task allows all three. A few repros (a do-nothing sweep, or a direct call to a scoring function) show the shortcut against the scoring code alone.
- Before filing, we check for duplicates against the repository's existing issues and pull requests.

How we report is set out in our [disclosure policy](https://holdout.cc/disclosure/).

## Layout

- `findings.json`: one record per issue (repository, title, environment, pattern, severity, filing date, state, fix pull requests, maintainer engagement, finding folder and any pull requests excluded by hand), with totals and a `generated_at` timestamp.
- `issues.txt`: every filed issue URL, one per line. A URL that is not yet in `findings.json` is added as a stub record flagged `needs_writeup`.
- `findings/<org>__<repo>__<slug>/`: `README.md` (summary, commit, pattern, severity, status) and, where the issue included them, the repro script(s) and `output.txt`.
- `scripts/update_status.py`: re-reads every issue with `gh api graphql`, refreshes `findings.json`, and regenerates the counts, the status line, the table and the severity line in this README and the status line in each finding. Run `python scripts/update_status.py` from the repository root with an authenticated `gh`. A [daily workflow](.github/workflows/update-status.yml) runs it and commits when anything other than the date changes, and at least once a week to keep the date current.
